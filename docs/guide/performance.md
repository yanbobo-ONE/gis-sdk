# 性能基准

分两层：**计算层**（空间量算、几何构造、地形剖面判据、姿态、回放、CZML 解析、位置归一化）不依赖渲染引擎，可以在 Node 里稳定复现，仓库自带脚本；**渲染层**（WebGL 帧率与内存）受设备与驱动影响，用验收台在浏览器里按场景测，方法与本机实测值见下文。

## 计算层：`pnpm bench`

```bash
pnpm build   # 脚本从 dist 导入，测的是发布产物
pnpm bench   # 可用 BENCH_MS=1000 加长每项测量时间
```

脚本对每项做 120 ms 预热，然后连续跑满 400 ms，输出**每次调用耗时**与**吞吐量**（吞吐量的单位写在名称里：调用 / 点 / 顶点 / 采样点）。

### 实测参考值

以下是一次实测输出（Apple M5 Pro、Node 22、darwin arm64）：

| 项目                                          | 每次调用  | 吞吐量           |
| --------------------------------------------- | --------- | ---------------- |
| `measureDistance()`（跨城两点）               | 0.08 µs   | 12.6 M 次/秒     |
| `measureArea()`（四边形）                     | 0.13 µs   | 7.7 M 次/秒      |
| `filterPointsInPolygon()`（1 万点）           | 713 µs    | 14.0 M 点/秒     |
| `convexHull()`（2 千点）                      | 305 µs    | 6.6 M 点/秒      |
| `clusterPoints()`（5 万点，1 公里网格）       | 3.96 ms   | 12.6 M 点/秒     |
| `simplifyPath()`（5 千顶点，10 米容差）       | 145 ms    | 34.4 k 顶点/秒   |
| `evaluateLineOfSight()`（64 个剖面点）        | 0.11 µs   | 9.0 M 次/秒      |
| `evaluateHorizon()`（32 个剖面点）            | 0.04 µs   | 27.8 M 次/秒     |
| `slerp()`（两姿态之间）                       | 0.10 µs   | 9.6 M 次/秒      |
| `headingPitchRollDegreesFromQuaternion()`     | 0.06 µs   | 17.5 M 次/秒     |
| `AttitudeDynamics.advance()`（10 ms 步长）    | 0.05 µs   | 20.0 M 次/秒     |
| `ReplayTimeline.sampleAt()`（600 样本，二分） | 0.02 µs   | 60.4 M 次/秒     |
| `SimulationClock.advance()`                   | < 0.01 µs | 257 M 次/秒      |
| `normalizePositions()`（1 万条）              | 47 µs     | 214 M 条/秒      |
| `czmlFromPositions()`（600 个采样点）         | 15 µs     | 40.0 M 采样点/秒 |
| `positionsFromCzml()`（600 个采样点）         | 19 µs     | 31.8 M 采样点/秒 |
| `tracksFromCzml()`（600 个采样点）            | 16 µs     | 38.1 M 采样点/秒 |
| `createTrackTimeline()`（600 个采样点）       | 1.35 ms   | 443 k 采样点/秒  |

### 怎么读这些数字

- **每帧只需要微秒级的**：`evaluateLineOfSight()`、`evaluateHorizon()`、`slerp()`、`sampleAt()`、`SimulationClock.advance()` 都在 0.1 µs 量级——按 60 fps 算，一帧的预算里它们连零头都用不到，可以放心放在渲染循环里。
- **单次调用在百微秒级的**：`filterPointsInPolygon()`、`convexHull()`。适合"数据变化时算一次"，不适合每帧算。
- **点聚合可以跟着视野走**：`clusterPoints()` 聚合 5 万点只要 4 ms，缩放或平移时重算一次完全来得及，不需要 Worker。
- **`simplifyPath()` 是本表最慢的一项**，145 ms/5 千顶点：RDP 在"容差小、几乎每个点都要保留"时接近最坏情况。轨迹抽稀建议放进 Worker（见[Worker 执行接口](./analysis-worker.md)），或先降采样再抽稀。
- **`createTrackTimeline()` 是"一次性建索引"的成本**（1.35 ms/600 采样点）：建好之后按 `sampleAt()` 查询只要 0.02 µs。
- **`normalizePositions()` 输出可转移的 `Float64Array`**，吞吐量高到可以在数据到达的瞬间跑一遍。

### 渲染层的口径与限制

- 本表只覆盖**纯计算**，不含 WebGL 渲染、网络、地形采样与 Cesium 对象创建；这些受设备、驱动与场景复杂度影响，无法用单一数字表达，渲染层的测法见下文。
- 数字来自一台开发机（Apple M5 Pro），不同 CPU 会成比例变化；**关注数量级与相对关系，不要当绝对承诺**。
- 每项测量的"每次调用耗时"包含调用本身的开销；参数规模写在名称里（点数、顶点数），换规模请按算法的复杂度外推。
- 基准跑的是 `dist` 产物（构建后的代码），与业务实际引入的形态一致；Node 与浏览器引擎不同，浏览器里的绝对值会有差异。
- 这项基准是**开发工具**，没有纳入 CI 门禁——不同负载的机器上做阈值断言只会得到 flaky 测试。

## 渲染层：浏览器端矩阵

验收台内置一个可复跑的矩阵探针：固定机位、**关闭自动降档**（开着它测到的是"降档之后"的开销），逐场景把瓦片等到收敛、再等满一个 60 帧采样窗口，最后读 SDK 自己的质量监测读数（`map.quality.snapshot`）——读的就是业务能读到的那个数，探针不另起一套计时器。

每个场景记六个帧指标（平均值 + P50 / P95 / 最长帧 / 长帧数）与一个主线程指标（浏览器 Long Tasks 计数）：

- **平均值**回答"快不快"；**P50 / P95 / 最长帧**回答"稳不稳"——均值会把卡顿摊平，60 帧里两帧卡到 200 毫秒，平均也只涨到 25 毫秒（仍有 40 fps）。
- **单次顿挫只会出现在最长帧上**：20 帧窗口里 1 帧卡顿落在 5% 之外，P95 照样是 16 毫秒。要判断"有没有偶发卡顿"，先看最长帧与长帧计数。
- **长帧与长任务对照**能区分卡在哪里：长帧多而长任务少，说明瓶颈在 GPU 或合成；两者都多，说明主线程被 JS 占住了。浏览器 Long Tasks API 目前只有 Chromium 实现，取不到时长任务列为 `undefined`，其余列照常。

```bash
pnpm example:prepare
npm --prefix .tmp/vanilla-consumer run dev -- --host 127.0.0.1 --port 4175
# 打开页面 → 点「性能矩阵（保持标签页可见）」
# 原始读数在面板该行的 data-matrix 属性里（JSON 数组）
```

**测量期间必须保持标签页可见**：标签页隐藏时浏览器会暂停渲染，采样窗口会被重置。

### 一次实测（2026-10-01）

环境：Chromium 内嵌视图 + ANGLE Metal（Apple M5 Pro）、画布 920×720、DPR 1、刷新率上限 120 Hz。长帧阈值取默认 50 毫秒。

| 场景                     | 帧率      | P50   | P95   | 最长帧 | 长帧 | 长任务 |
| ------------------------ | --------- | ----- | ----- | ------ | ---- | ------ |
| 空场景（椭球地形）       | 119.9 fps | 8.30  | 9.10  | 10.10  | 0    | 0      |
| 点位 5 000               | 119.5 fps | 8.40  | 9.00  | 10.00  | 0    | 0      |
| 点位 20 000              | 120.0 fps | 8.30  | 9.30  | 9.90   | 0    | 0      |
| 点位 100 000             | 82.6 fps  | 12.10 | 13.10 | 14.20  | 0    | 0      |
| 折线 2 000               | 120.3 fps | 8.30  | 8.60  | 9.30   | 0    | 0      |
| CZML 500 实体            | 120.2 fps | 8.30  | 9.50  | 9.60   | 0    | 0      |
| WMS 影像                 | 120.1 fps | 8.30  | 8.90  | 9.30   | 0    | 0      |
| 雨（环境效果）           | 120.0 fps | 8.30  | 8.60  | 8.80   | 0    | 0      |
| 点位 100 000 + 影像 + 雨 | 83.3 fps  | 11.90 | 12.80 | 14.20  | 0    | 0      |
| 同上（low 档）           | 54.6 fps  | 18.30 | 19.00 | 19.40  | 0    | 0      |
| 同上（仅分辨率 0.75）    | 54.4 fps  | 18.40 | 18.80 | 20.40  | 0    | 0      |
| 同上（默认档·复测）      | 83.5 fps  | 11.90 | 12.90 | 13.00  | 0    | 1      |

帧耗时单位统一为毫秒；JS 堆该次为 190–290 MB（受 GC 时机影响，未列入本表）。

### 怎么读这张表

- **轻场景全部顶在刷新率上限**：5 千点、2 万点、2 千折线、500 个 CZML 实体、影像与雨效果都是 120 fps（8.3 ms），差异落在噪声里——这些规模在该 GPU 上不是瓶颈，帧率已无区分度。
- **10 万点是单图层里唯一突破上限的场景**：82.6 fps（P50 12.1 ms）；组合场景（10 万点 + 影像 + 雨）83.3 fps，与只放 10 万点几乎一样，说明影像与雨在这个机位下没有可测出的增量。
- **帧率低但很稳，是吞吐问题不是卡顿问题**：所有场景的 P95 只比 P50 高约 1 毫秒、最长帧离 P50 也在 2 毫秒以内，长帧（≥50 毫秒）与长任务几乎全程为 0（12 个场景里只出现 1 次长任务）。本环境下没有观察到顿挫，重场景是"稳定地慢"。
- **50 毫秒阈值在这台机器上太宽**：P95 都在 20 毫秒以内，长帧列自然全是 0。要按 60 Hz 的节奏看齐不齐，把阈值降到 16.7 毫秒更合适——`createMap({ quality: { longFrameMs } })` 可以调整（见[渲染质量](./quality.md)）。

### 漂移：只有同一次运行内的比较有效

- **同一次运行内**：两条默认档对照行（`点位 100 000 + 影像 + 雨` 与它后面的 `同上（默认档·复测）`）相差不到 1%（83.3 / 83.5 fps），测量本身可复现。
- **跨运行差得多**：三次独立运行里，"点位 100 000 + 影像 + 雨"分别给出 **68.7 / 83.3 / 69.4 fps**——同机同环境最大差约 20%，而且不是均匀噪声（两次落在 69 附近、一次明显偏快）。绝对值会整体平移，**不要拿本页表格的历史数字当阈值基线**；每次比较都用同一次运行里的行相互对照。
- 相对关系稳定得多：`low` 档相对默认档的比值三次运行分别是 0.70 / 0.66 / 0.69，方向与幅度都一致——这也是"本环境下降档更慢"这个结论可信、而绝对帧率不可直接引用的原因。

### ⚠️ 一个反直觉结果：本环境下降档反而更慢

上表里 `low` 档（`resolutionScale 0.75`）在同一重场景下是 **54.6 fps**，比默认档的 83.3 fps 慢约三成。为排除顺序与预热的影响，矩阵里有两条对照行：

- **仅分辨率 0.75**（只把 `resolutionScale` 降到 0.75、其余参数保持默认）：54.4 fps——与 `low` 档一致，说明差异可以归因到**分辨率缩放这一个参数**，而不是该档位的其它参数；
- **默认档·复测**（放在 low 档之后）：83.5 fps——切回默认档后立刻恢复，说明不是跑久了变慢。

也就是说：在**这台机器 + 这个渲染路径**上，把分辨率降到 0.75 并不提速，反而掉三成（两次独立运行分别掉 30% 与 34%，方向一致）。这与 `quality` / `balanced` / `low` 三档在参照项目生产环境的结论方向相反，因此**不要假定"降档一定更快"**：

- 自动降档（`createMap({ quality })` 的按帧率升降档）在目标环境上线前应单独验证一次：如果该环境上降档方向相反，自适应会一路降到最低档而帧率不升。
- 需要真正降负载时，优先减图层数据量（例如按视野聚合、抽稀），而不是依赖分辨率缩放。

机制没有定论（本次只做了行为层面的隔离，未做渲染管线级别的归因）。注意画布后备缓冲小于 CSS 尺寸时，上采样由浏览器合成器负责，内嵌视图与原生窗口的合成路径可能不同——**在目标浏览器窗口里复核一次再据此改策略**。

### 渲染层的口径与限制

- 单一机器、单一浏览器、单一渲染路径（内嵌 Chromium + ANGLE Metal）。不同 GPU、驱动与浏览器会给出不同结论，**这是方法加一份记录，不是跨环境承诺**。
- 固定机位（116.4°E / 39.9°N 上空 900 km 俯视），所有行从同一视角看同一片区域；换机位会改变可见瓦片数与图元数量，读数不可比。
- 帧率与帧耗时取自 SDK 的质量监测（60 帧滑动窗口），窗口未满或检测到长卡顿时会重置，被重置的窗口不计入读数；分位数用最近秩口径，详见[渲染质量](./quality.md)。
- **JS 堆只代表 JS 侧**（且只有 Chromium 暴露 `performance.memory`），不含 GPU 显存与纹理；堆数字受 GC 时机影响，列与列之间的波动不能当泄漏证据。
- **长任务只有 Chromium 有**：Long Tasks API 是 Chromium 独有，其它浏览器上该列为 `undefined`；它不是 SDK 能力，是探针对浏览器 API 的读取。
- **本矩阵不设阈值**：可接受的帧率与机型范围属于产品决策。给定时按照上文方法重跑一次，与**同一次运行内的对照行**比较——跨运行的绝对值会整体平移（见上文漂移一节）。
- 矩阵本身不进 CI：它需要真实浏览器与 GPU，和计算层基准一样属于手工验收工具。

## 当前边界

- **多浏览器 / 多机型矩阵仍是手工**：本页记录的是一个环境的一次运行；Chrome / Firefox / Safari 与不同 GPU 的对照需要按目标机型各跑一遍验收台矩阵，尚未自动化。
- **没有数据规模承诺**：点位图层的单层上限（20 万点）是渲染路径的实测边界，CPU 侧的吞吐请以上表为准自行折算。
